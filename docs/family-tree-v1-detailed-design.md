## 1. 目的・対象範囲

### 1.1 [確定] プロダクト

汎用的な家系図エディター。PC・スマートフォン共通のタップ操作で、人物・家族・親子関係を構築する。個別の一族や実在人物に依存しない。

- HTML / CSS / JavaScript、jQueryを想定。
- GitHub Pagesで公開。Ver.1は`v1/`に配置。
- `v2/`、`other_test/`等は別の実験用。
- 外部ライブラリはルート`vendor/`、必要な自作共通処理は`shared/`。
- 架空サンプルは`samples/`、仕様書は`docs/`。
- 実在親族の個人情報をGitHubへ保存しない。

### 1.2 [確定] 保存と通信

- 1つのJSONを読込・編集・ダウンロードして利用する。
- 起動時に`samples/sample_family.json`を読み込む。
- JSONアップロード成功時は現在の家系データを置き換え、家系図・名簿を再描画する。
- 破棄確認は行わない。再読込時はサンプルへ戻る。
- localStorage / IndexedDBへの永続保存、暗号化、外部サーバーへの家系データ送信を設けない。

### 1.3 [実装設計] Ver.1対象外

自由座標の保存、ドラッグ配置、人物の入れ替え、共同編集、ログイン、クラウド保存、人物写真、GEDCOM、画像/PDF出力、検索範囲による部分家系図、履歴のUndo/Redo、自動的な続柄推定・翻訳は対象外。

名簿検索・関係選択時の検索は対象に含める。名簿検索は家系図の描画スコープを変更しない。

### 3.3 型とNULL

フィールド名・JSON型・上限・正規化は以下の契約に従う。

| 対象 | 型・制約 |
|---|---|
| schema_version | 整数`1`。文字列`"1"`は拒否 |
| 3テーブル | オブジェクトの配列。空配列は有効 |
| id / 外部キー | 正のsafe integer。外部キーは許可された箇所のみNULL |
| auto_increment | 3キーすべて必須。正のsafe integerで、対応する最大IDより大きい |
| persons.id | 必須。同一persons内で一意 |
| name / nickname / gender / residence / birth_place / occupation / notes | 文字列またはNULL |
| birth_date / death_date | 部分日付を表す整数またはNULL。詳細は3.5 |
| is_alive | `true` / `false` / `null`。`0`、`1`、文字列は拒否 |
| families.id | 必須。同一families内で一意 |
| partner1_id / partner2_id | persons.idまたはNULL |
| marital_status | 文字列またはNULL |
| family_children.id | 必須。同一family_children内で一意 |
| family_id / child_id | 必須。存在するfamilies.id / persons.id |
| sort_order | 必須。正のsafe integer。同一家族の正規形は`1..n` |
| relation_type | 文字列またはNULL |

- `persons`のID以外は原則NULL許容。氏名未入力の人物も作成できる。
- 全NULL許容フィールドは、読込で省略されていればNULLに補う。書出しでは全フィールドを出力。
- 文字列の前後空白は除き、空文字列・空白だけの文字列はNULLにする。内部空白、改行、ベトナム語の記号・声調は保持。
- 表示名は`name → nickname → 翻訳済み「名前未設定」＋ID`。仮人物は正式IDの代わりに「未配置」を表示。
- 同名人物は別IDなら許容する。氏名で人物を結合しない。
- `partner1`と`partner2`に性別や父母の固定的意味を持たせない。
- IDの発行後に次のカウンターを保持できなくなる場合は新規発行を拒否する。整数オーバーフローを発生させない。

### 3.4 [実装設計 D06] 選択肢

| 項目 | UIプリセット | その他の文字列 |
|---|---|---|
| gender | NULL、不明指定なし / `male` / `female` / `other` | 自由入力・保持 |
| marital_status | NULL / `married` / `divorced` / `separated` / `unmarried` / `widowed` | 自由入力・保持 |
| relation_type | NULL / `biological` / `adopted` / `step` / `foster` | 自由入力・保持 |

コード値の標準選択肢ラベルだけを翻訳する。自由入力値はそのまま表示。未知の値をNULLや既知値に置換しない。`gender`のNULLは男性／女性のどちらかへ推定しない。

婚姻状態は家族単位の属性であり、法的婚姻の存在を作成条件にしない。`widowed`から人物の生死を自動更新しない。`relation_type`はその家族と子の関係全体を示す。親2人それぞれ別の種別を持たせることはこのスキーマでは扱わない。

### 3.5 [確定仕様] 部分日付

[確定] 数値`YYYYMMDD`。年のみは`YYYY0000`、年月のみは`YYYYMM00`。

[実装設計] 年は1〜9999、西暦グレゴリオ暦。保存は整数なので先頭ゼロは存在せず、表示時に桁を補う。

- `null`: 完全不明。
- `19800000`: 1980年。
- `19800500`: 1980年5月。
- `19800521`: 1980年5月21日。
- `19800015`: 月なし・日ありなので拒否。
- `0`、負数、小数、文字列、存在しない日（例: 20230229）を拒否。
- 月が0なら日も0。月が1〜12で日が0なら年月。日ありなら閏年も検証。
- 入力は年・月・日の分割欄。月・日は「不明」を選択できる。日付入力1欄だけにしない。
- 生年月日と没年月日をそれぞれ可能な最小日・最大日の区間に展開し、`出生最小日 > 死亡最大日`なら拒否。区間が重なるだけなら許容。
- `is_alive=true`かつ`death_date!=null`は矛盾として拒否。`false`かつ没年月日不明、`null`かつ没年月日ありは許容。値は自動推定しない。
- 子と親の年齢差、婚姻時年齢、未来の日付はVer.1の整合性エラーとしない。

### 3.6 [確定] 削除・参照と[実装設計]制約

[確定]

- 人物削除: personsから削除。familiesの該当パートナー枠をNULL化。child_idが対象人物のfamily_childrenを削除。
- 家族削除: familiesとそのfamily_childrenを削除。人物は残る。
- 親子関係削除: 対象family_childrenだけを削除。
- 兄弟順に影響する家族は削除後に再採番。

[実装設計 D04/D08/D14]

- パートナー2枠が同じ人物になることを禁止。
- `(family_id, child_id)`は一意。
- 両パートナーが存在する家族は、順不同の人物ペアが一意。`(1,2)`と`(2,1)`を重複作成しない。
- 片親家族や両親不明家族は複数存在できる。人物削除により同じ片親構成になっても統合しない。
- 両パートナーNULLの家族、子が0人の家族を許容。空になった家族を自動削除しない。
- 子がその家族のパートナーでもある状態を禁止。
- 祖先循環を禁止。実子・養子・その他すべてのrelation_typeを同じ向きの親子エッジとして判定する。
- 複数の親家族、複数のパートナー家族は許容。血縁のある人物同士のパートナー接続も許容する。
- 全NULLの親家族からは、未知人物IDや仮のpersonsを自動作成しない。

祖先循環判定は各familyについて「既知の各パートナー → 各child」の有向グラフを構築する。全体をKahn法等で検査し、全人物を処理できなければ拒否する。親のない家族だけでは祖先エッジを作らない。

## 4. 実行時状態・ID・更新単位

### 4.1 [実装設計 D09/D11] 状態分離

```text
AppState
  document: 正規化した保存対象JSON
  drafts: 仮人物のMap（draftKey → 人物属性、idなし）
  ui:
    view: tree | roster
    language: ja | en | vi
    interaction: 操作状態
    selectedPersonId / selectedDraftKey
    rosterQuery
    viewport: scale, translateX, translateY
    notices / importWarnings
  derived:
    indexes
    components
    layout
```

`ui`、`derived`、`drafts`はJSONに出力しない。`is_placed`、世代、座標、ビュー内カードIDをpersonsへ追加しない。配置済みかどうかは「正式personsにあるか」で判断する。

### 4.2 [確定仕様] 仮人物

[確定] 登録直後はメモリ上の未配置人物。配置した人物だけ正式personsとして保存対象。

[実装設計]

1. 作成フォームを保存すると`draft-1`等の実行時専用キーを発行し、draftsへ入れる。
2. 名簿の未配置欄に表示し、その人物を選択した配置モードへ入る。
3. 配置候補を選んで最終検証が通った時、personsのIDを発行してdocumentへ追加し、必要な関係も同じ更新で作る。
4. 成功後だけdraftsから除去。失敗・キャンセルでは仮人物を保持。
5. 起点として配置すると、personsへ追加するだけでよい。孤立人物も正式な保存対象。
6. ビュー切替や配置取消では消さない。JSON置換成功・ページ再読込では消える。仮人物を個別に破棄する操作も用意。

「未配置」と「関係を持たない正式人物」は別物。後者は削除操作をしない限りJSONに残す。

### 4.3 [実装設計] コマンドの原子性

データ操作は常に「候補状態を生成 → 整合性検証 → 一度だけcommit」。検証失敗時はdocument、drafts、auto_incrementのすべてを変更しない。

- 正式IDは候補状態に対して予約し、commit時にのみ実状態へ反映。
- 成功したIDは削除後も再利用しない。失敗してcommitされなかったIDは発行済みとみなさない。
- 人物追加＋家族追加＋親子追加など、1操作の途中状態を画面へ露出しない。
- commit後はインデックス・レイアウトを再生成し、家系図と名簿を更新する。
- 関係選択はUIスナップショットを信用せず、実行直前に参照先と重複を再検証。

## 5. 操作とデータ更新

### 5.1 [確定 D02/D05] 操作の意味

| 操作 | 意味 | 既存関係 |
|---|---|---|
| 新規配置 | 仮人物を正式人物にし、選んだ関係へ入れる／独立起点にする | 既存データを保持 |
| 移動 | 正式人物の親家族・兄弟順を変更 | 5.3の0/1/2件ルール |
| 子として接続 | 正式人物を対象家族の子に追加 | 他家族の親子関係をすべて保持 |
| パートナーとして接続 | 家族の空き枠を埋める／新家族を作る | 他の家族所属・親子関係を保持 |
| 親関係の解除 | 特定のfamily_childrenを削除 | 他の関係を保持 |
| パートナー枠の解除 | 選択した家族の指定枠をNULL化 | 家族・子・人物を保持 |

カードの自由な位置移動は保存されず、関係に意味のない空白位置への移動は用意しない。パートナー枠を移し替える場合は「関係を管理」で旧枠を解除し、新しい接続を作る。

### 5.2 [実装設計] 人物メニュー

- 詳細／編集。
- 移動（親家族・兄弟順）。
- パートナーを接続。
- 子を接続（自分がパートナーである家族へ、相手を子として追加）。
- 親家族へ接続（自分を子として追加）。
- 親を追加（既存の親家族の空き枠へ追加、または新しい親家族を作る）。
- 関係を管理（家族・親子レコードの一覧、属性編集、解除）。
- 人物を削除。

仮人物メニューは「編集」「配置」「破棄」。名簿からも同じ操作へ入れる。

### 5.3 [確定] 親子関係の移動

操作対象personの現在のfamily_childrenを数える。対象familyへの接続が既にあるかを先に判定する。

| 条件 | 処理 |
|---|---|
| 同じfamilyに既存レコードあり | 新規接続せず、その家族内でsort_orderだけ変更 |
| 対象familyに未接続・既存0件 | 新しいfamily_childrenを作成 |
| 対象familyに未接続・既存1件 | 既存レコードのfamily_idとsort_orderを更新 |
| 対象familyに未接続・既存2件以上 | 既存関係を保持し、新しいfamily_childrenを追加 |

[実装設計] 既存1件の更新ではレコードID・child_id・relation_typeを保持。新規作成ではrelation_typeをNULLにし、関係編集から指定可能とする。別の種別に勝手に変えない。

既存2件以上の場合は選択モードに「既存の親関係は残り、新しい関係が追加されます」と表示する。旧関係の自動解除・移動元の推定はしない。

対象と旧家族の両方を必要に応じて再採番する。兄弟順変更だけでは他の親家族を変更しない。

### 5.4 [実装設計] 兄弟順の定義

- 家族内の現在順は`sort_order`昇順。正規形は1始まりの連番。
- n人の子に対して挿入候補は先頭・間・末尾のn+1箇所。
- 同一家族内の並び替えでは、対象レコードを一旦除外したリストに対して挿入候補を作る。左右の同じ場所が二重に出るのを防ぐ。
- 候補は`beforeChildLinkId`（末尾はNULL）で指定する。画面の配列添字を更新APIへ渡さない。
- 別家族への1件更新では、旧家族から対象を除き旧側を再採番した後、対象家族へ挿入して再採番。
- 親子関係削除後も残った兄弟の相対順を保持。
- 兄弟順変更は生年月日で自動的に上書きしない。

### 5.5 [確定 D04] パートナー接続

人物Aのメニューから開始。

1. 接続先家族を選ぶ。「Aの所属家族の空き枠」および「新しい家族を作る」を表示。
2. 相手Bをカードタップまたは名簿検索で選ぶ。未配置人物を選ぶ場合は正式化も同時実行。
3. 空き枠ならその枠をBに更新。新家族なら`partner1_id=A`、`partner2_id=B`、`marital_status=null`で作成。
4. 同じ2人の家族がある場合は追加せず、既存家族を表示・選択する。入れ替えや黙った統合はしない。

家族の2枠が埋まっていれば上書き候補を出さない。3人目は新しい家族を作る。Bが別のパートナーを持つことは拒否理由にならない。性別・生死・婚姻状態を接続条件にしない。

### 5.6 [確定 D05] 親子接続の選択UI

**「子を接続」**

1. 起点人物がパートナーである家族を選択。1家族でも選択内容を表示し、2家族以上なら明示選択。
2. 対応する家族がない場合は、起点人物だけを親とする新家族を作る候補を表示する。
3. 子となる人物をカードまたは検索で選ぶ。
4. 初期は末尾へ接続。位置を変更したければ挿入位置を選ぶ。親家族の追加として処理し、他家族を解除しない。

**「親家族へ接続」**

1. 起点人物を子として扱う。
2. 家族の線・家族チップをタップ、または人物をタップして「この人物がパートナーである家族」の候補を選ぶ。
3. 人物に複数の所属家族があれば自動決定しない。子として属する家族を「その人物の子を持つ家族」と取り違えない。
4. 接続対象がない場合は、選択人物を既知の親とする新家族を作る候補を示す。
5. 挿入位置を選び、`addChild`を実行する。

**「親を追加」**

1. 起点人物の親家族を選び、その家族の空きパートナー枠へ人物を入れる。
2. 既存親家族がない、または別家族を作りたい場合は「新しい親家族」。
3. 新家族では選んだ人物をpartner1、partner2をNULLにし、起点人物の子レコードを追加する。
4. 両枠が埋まった家族に3人目を入れない。既存家族のもう一人の親を置換しない。

通常の接続も、配置モード・移動モードと同じ検証器を使用する。祖先循環になる候補は無効化し、理由を表示。

仮人物を新しい親として追加する場合は、人物の正式化・新家族・起点人物の親子レコード追加を1コマンドでcommitする。新家族だけ先に作成してから相手選択を待つことはしない。家族を選び直したり選択を取り消しただけではdocumentを変更しない。

### 5.7 [実装設計 D14] 解除・削除

| 操作 | UIと処理 |
|---|---|
| 人物削除 | 確認画面に本人、パートナー枠の解除数、削除される親子レコード数を表示。3.6の処理を原子的に実行 |
| 家族削除 | 家族ID・既知の親・親子関係の削除数を表示して確認。人物が残ることを表示 |
| 親子関係解除 | 関係一覧から特定IDを解除。対象だけ削除し兄弟順を再採番 |
| パートナー解除 | 家族IDと枠を指定してNULL化。人物・家族・子を削除しない |
| 属性編集 | 人物、marital_status、relation_typeをそれぞれ編集。親子種別変更でもsort_orderは維持 |

削除後に関係がなくなった正式人物は独立人物として描画。人物を家系図から一時的に隠す「未配置に戻す」機能は設けない。

独立した起点にしたい場合は「関係を管理」で対象の親関係を解除する。複数親関係がある場合は一覧から個別に解除する。パートナーや子が残るなら、その人を含む家系全体は引き続き接続しているため、完全に独立した人物にはならない。

## 6. 配置候補と操作状態

### 6.1 [実装設計 D03] 候補データ

```text
PlacementCandidate
  key: 操作中に一意な候補キー
  kind: root | child-slot | partner-slot | new-partner-family
  familyId?: 正式family ID
  partnerSlot?: partner1_id | partner2_id
  anchorPersonId?: 正式person ID
  beforeChildLinkId?: 正式family_children ID | null
  labelKey / labelParams
  enabled / disabledReasonKey
  screenAnchor?: 描画対象のビューキー
```

座標は候補の意味や識別子にしない。候補はperson ID・family ID・childLink IDで一意に識別する。

### 6.2 候補の生成表

| モード | 出す候補 | 出さない候補 |
|---|---|---|
| 仮人物の配置 | 独立起点、各家族の子挿入位置、空パートナー枠、各人物との新しいパートナー家族 | 埋まったパートナー枠、自分との関係、同じ人物への重複 |
| 正式人物の移動 | 各家族の子挿入位置 | パートナー枠、自由空白、独立起点（解除で扱う） |
| パートナー接続 | 操作で選んだ家族枠または新家族に対する相手人物 | 自分自身、重複ペア、循環を生む空き枠への追加 |
| 親子接続 | 対象家族または家族を絞るための人物、子の挿入位置 | 同一家族に既にいる子、自己親子、祖先循環 |

「仮人物を新家族の親として既存人物の上に置く」操作は、「親を追加」から仮人物を選ぶことで実現する。親用の汎用空白スロットを人物の真上へ無条件には作らない。

### 6.3 画面への提示

- 論理上は全候補を生成するが、キャンバス上には可視範囲の候補を主に描く。
- 家族の子ラインの前・間・後に挿入マーク。既知の親がいない家族は「親不明・家族#ID」のチップを起点にする。
- 子が0人なら「最初の子を追加」を1つ表示。
- パートナーの空き枠は家族チップ近傍へ表示。新家族は人物に付く「パートナーとして追加」の候補として表示。
- 独立起点は固定ツールバーの「新しい家系として配置」にする。空白をタップした座標を保存しない。
- 画面外・縮小時・候補が密集する場合のため、同じ候補を一覧でも選べる。検索・家族選択・挿入順は一覧で完結可能。
- 無効候補の理由は「自分自身を親にはできません」「祖先との循環になります」等、固定辞書キーで表示。

候補ごとに全JSONを複製・全検証して動作を重くしない。選択人物に対する到達可能集合を操作開始時に求め、家族ごとの既知親との交差で循環候補を絞る。「親関係1件の移動」は旧親子レコードを除いた仮のグラフで候補判定し、旧エッジが残ったグラフで誤って禁止しない。同じ人物ペアの親子エッジが別familyにもある場合は、その別familyのエッジを残す。パートナー枠への追加は、その人物から家族の全ての子への新エッジを検査する。キャッシュはdocumentの変更ごとに無効化し、commit直前の全体検証を最終的な正とする。

### 6.4 [実装設計] 状態遷移

| 状態 | 入力 | 次状態／処理 |
|---|---|---|
| idle | 人物カード | person-menu |
| person-menu | 移動／配置 | choose-placement |
| person-menu | パートナー接続／子接続／親接続 | choose-familyまたはchoose-person |
| choose-family | 対象family／新家族選択 | choose-personまたはchoose-placement |
| choose-person | 有効な相手選択 | 必要ならchoose-placement、不要ならcommit |
| choose-placement | 有効な候補タップ | commit |
| commit | 検証成功 | 再描画してidle |
| commit | 検証失敗 | エラーを表示して直前の選択状態を保持 |
| 操作中 | キャンセル／Escape | idle。仮人物は保持 |
| 操作中 | 家系図／名簿切替 | 選択モードを保持し同じ対象を選択可能 |
| 任意 | JSON置換成功 | 選択・仮人物・検索をリセット、idle |

単なる画面パンは選択モードを終了させない。背景の単発タップでメニューは閉じても、配置モードの破棄は明示的なキャンセルにする。連打中はcommitを重複実行しない。

## 7. 自動配置の詳細

### 7.1 [確定] 原則

- 関係から構築し、世代番号・表示座標をJSONに持たない。
- 描画スコープ内で親子関係から世代を計算する。
- パートナーは横、親子は縦に接続。
- 複数の独立家系を描ける。関係追加で結合できる。
- データ更新後は原則全体再描画。可能な限りズーム・位置を保持。

### 7.2 [確定 D01] 対応範囲と保証

同一人物カードは1枚だけ配置する。通常の関係ではパートナーを同じ行、子を1世代下へ置き、兄弟順を左から右へ反映する。

Ver.1では、これらの世代・左右順が両立する関係を自動配置の対象にする。片親・両親不明、再婚、複数の親家族、複数の独立家系は、条件が両立する限り対象に含む。線の交差を完全になくすことは保証しない。

世代のずれる親族間パートナー関係や、複数家族での逆向きの兄弟順など、条件が両立しない例外への専用表示・自動修復は実装しない。必要になった時に実例を基に検討する。例外対応のために人物を再掲したり、関係やsort_orderを変更しない。

### 7.3 入力・出力

```text
layout(document, metrics) -> LayoutResult
  components[]: componentKey, bounds
  personNodes[]: viewKey, personId, x, y, width, height, componentKey
  familyAnchors[]: viewKey, familyId, x, y, componentKey
  edges[]: edgeKey, familyId, childLinkId?, kind, points[], styleKey
  relationTargets[]: familyId, childLinkId?, anchor, componentKey
  bounds
```

`viewKey`は実行時のみ。人物は`person:<id>`、家族アンカーは`family:<id>`を使う。人物操作は常に`personId`へ戻し、1人物を複数のカードへ分けない。

レイアウト関数はDOMやjQueryへ依存せず、状態を変更しない。入力配列の並びが違っても、IDとsort_orderが同じなら同じ出力にする。

### 7.4 ステップA: インデックス・連結成分

1. `personsById`、`familiesById`、`childrenByFamily`、`parentLinksByChild`、`familiesByPartner`を作る。
2. 人物ノードPと家族ノードFの二部グラフを作る。既知パートナーと子はそれぞれ家族へ接続。
3. 無向で連結成分を抽出。孤立人物も1成分、誰もいない空家族も1成分とする。
4. 成分内人物の最小IDを主キー、人物がない場合は最小family IDを用いる。人物あり成分、人物なし成分の順に安定整列。

構築・探索は反復処理にし、深い家系でJavaScriptの再帰スタックへ依存しない。

### 7.5 ステップB: 世代制約

世代を整数ポテンシャル`g`として、各成分に以下の差分制約を置く。

- 家族Fの既知パートナーP: `g(P) = g(F)`。
- 家族Fの子C: `g(C) = g(F) + 1`。
- 親が両方不明でも家族Fを仮想アンカーとして残す。personsの仮人物は作らない。

ノード1つを0として、制約を逆向きも含めてBFSで伝播する。既訪問ノードへ異なる値が要求されたら**描画制約不一致**。祖先循環検証とは別物であり、有効な家族データでも発生する。

一致したら成分の最小世代を0へ平行移動する。年齢・性別・IDから世代を推定しない。切り離し・結合後は再計算する。

伝播が矛盾するケースは7.9の対象外例外とする。検出時は処理を有限で打ち切り、専用レイアウトの追加で解決しようとしない。

### 7.6 ステップC: 兄弟順と横並び

1. 同じ世代の人物間に、家族ごとの子リストの隣接ペアについて`child[i] < child[i+1]`という左右順の有向エッジを張る。
2. 同じ順序エッジは重複排除する。兄弟以外の左右位置は固定しない。partner1が必ず左という制約も付けない。
3. 各世代で順序グラフをトポロジカルソートする。順序制約が循環するケースは7.9の対象外例外とする。
4. 初期の同順位はID昇順。親・子の前回の横位置の平均を優先値として、上→下／下→上を2往復（合計4 sweep）実行する。
5. 各sweepでもKahn法で選択可能なノードだけを取り出し、優先値→直前順→IDで選ぶ。単純な平均値ソートによって兄弟順を破らない。
6. 同世代パートナーの近接は同順位時の補助評価にできるが、兄弟順より優先しない。複数パートナーを常に隣接させる保証はしない。

順序の矛盾を解消するためにfamily_childrenのsort_orderを勝手に書き換えない。

### 7.7 ステップD: 座標

初期寸法案: 人物カード176×104、同世代の最小間隔32、線レーン間隔24、成分間隔96（レイアウト座標px）。フォントや端末検証により調整可能な設定値にする。

- 各世代で人物および必要な親不明家族アンカーを順に並べ、カード同士に32以上の間隔を確保。
- 親不明アンカーは幅48のレイアウト要素として扱い、関連する子の平均横位置を優先値にする。人物の兄弟順制約は変えない。
- 行ごとに全幅を計算し、成分の最大行幅に中央寄せ。
- y座標は行番号×固定値にせず、その行から出る家族数に応じた線レーンの高さを加算する。
- 通常表示の例として、行間領域は`余白24 + 家族数×24（パートナーバス）+ 余白24 + 子がいる家族数×24（子バス）+ 余白24`以上。
- 最終行にも子なし家族のパートナーバス分の空間を確保。
- 親不明・子なしの家族は家族チップを1つ描き、人物を捏造しない。
- 成分は左から右へ安定順で並べる。成分数が多い場合の画面幅による折返しはVer.1ではせず、パン・全体表示・名簿検索で移動。

カードは固定高さで氏名を最大2行に省略し、完全な情報は詳細シートで表示。人によってカード寸法を変えて衝突させない。

### 7.8 ステップE: 線と家族アンカー

- 家族をID順に並べ、行間に専用の水平レーンを割り当てる。異なる家族のバスを同じy座標へ重ねない。
- 既知の親カード下端から短い縦線を下ろし、その家族専用レーンで横につなぐ。2人が離れていても、バスをカードの上に通さない。
- その横バスの中央に家族アンカーを置く。片親はその人の近く、両親不明は仮想アンカーの位置を使う。
- 子のいる家族は、家族アンカーから下方の専用子バスへ縦につなぎ、各子カード上端へ分岐する。子バスはその家族の子の最小x〜最大x。
- family_childrenごとの種別は子へ降りる枝に適用。共通バスは中立線。`adopted`は破線、その他はラベルで区別する等、凡例を出す。
- 同一家族の1本だけの子枝にもchildLinkIdを付け、個別解除可能にする。
- 線の交差は許容するが、交差点に接続点を描かない。家族アンカーと実際の分岐だけ接続点を付ける。
- パートナー同士の接続が複数家族分ある場合も、家族ごとに独立したバス・チップで識別する。
- 線をクリックできなくても、家族チップと関係一覧から同じ編集へ到達できるようにする。

同一人物に複数の入出力がある場合、family ID / childLink ID順でカード上端・下端のポート位置を分ける。異なる家族の縦幹も、同じxで同じ区間を共有しないよう中央近傍へずらす。必要ならバスの幅と成分boundsを広げる。異なる家族の線を1本にまとめて関係の区別を失わせない。選択した家族の線だけを強調し、他の線は薄くできるようにする。

この方式は最短線・交差最少を厳密最適化しない。カードを避けて全関係を決定的に描けることをVer.1の優先要件とする。

### 7.9 [確定 D01] 対象外例外

世代・兄弟順が両立しない特殊ケースへの対応は、実際に必要になってから検討する。家族単位への表示分割、同一人物カードの再掲、特殊な世代調整、例外専用の選択UIは今回作らない。これらのケースはVer.1の描画受入条件に含めない。

祖先循環・参照切れ等のデータ整合性エラーと、描画上の条件不一致は区別する。計算が矛盾した場合に無限ループ・データ削除・自動修復をしない。一般の描画失敗として通知し、元のJSONと名簿・JSON保存へのアクセスは保持する。専用の回復フローは設計しない。

### 7.10 例外一覧

| 状態 | データ扱い | 描画 |
|---|---|---|
| 孤立人物 | 有効 | 1枚の独立家系 |
| 複数の独立家系 | 有効 | 別成分として配置 |
| 片親／両親不明 | 有効 | 家族アンカー＋子 |
| 子なし／人物なし家族 | 有効 | 家族チップを残す |
| 複数の親家族・複数パートナー | 有効 | 制約が解ければ通常表示 |
| いとこ同士等のパートナー | 有効 | 制約判定による。近親であること自体は拒否しない |
| 世代条件の競合 | データ上の祖先循環とは区別 | Ver.1の特殊描画対応外。発生時に検討 |
| 複数家族で兄弟順が逆 | 各家族の順番は保持 | Ver.1の特殊描画対応外。発生時に検討 |
| 自己親子／自己パートナー | 拒否 | データ更新しない |
| 祖先循環 | 拒否 | 読込も操作も原子的に失敗 |
| 参照切れ・重複親子 | 拒否 | 勝手にレコードを削除しない |

### 7.11 ズーム・表示位置の保持

- 表示変換を`screen = world × scale + translate`の一系統にする。SVGとHTMLに同じ変換を適用。
- 再描画前に、表示中心へ最も近い人物のviewKey、personId、スクリーン位置、scaleを記録する。
- 再描画後は同じ人物のviewKeyを使い、そのアンカーが同じスクリーン位置になるようtranslateを調整。
- 操作対象を明示選択している場合は、その人物をアンカーに優先してよい。
- 人物が削除された場合は旧中心のworld座標を維持し、全体が画面外になる場合だけ最小限補正。
- 家系の結合で位置が大きく変わってもscaleは保持。自動で全体表示にしない。
- 初回サンプル読込、JSON置換成功、「全体表示」ボタンだけフィットを実施する。
- 言語変更・画面回転でも同じアンカー方式を使う。名簿から「家系図で表示」は対象へ移動する明示操作とする。

## 8. UI・スマートフォン・多言語

### 8.1 [実装設計 D10] 共通画面

- 上部: アプリ名、家系図／名簿切替、言語、メニュー。
- メニュー: 人物追加、JSON読込、JSON保存、全体表示、ヘルプ。
- キャンバス操作: ＋／−、全体表示、操作中の説明、キャンセル。
- 名簿: 名前・愛称の検索、正式人物と未配置人物の区分、詳細・編集・家系図で表示。
- 正式人物の初期順はID昇順。検索はname/nicknameの部分一致、大文字小文字を区別せず、声調記号は勝手に落とさない。
- 関係選択の一覧ではID、表示名、家族ID、既知の親、子数、marital_statusを識別補助として表示する。
- 自分が扱うデータは自分でJSON保存すること、未配置人物は保存対象外であることをヘルプと保存後通知に明記。

### 8.2 モバイル

- 幅360 CSS pxを最小の検証幅とする。ヘッダー・フォームは横にはみ出さず、家系図キャンバスだけ縦横へ移動可能。
- 人物メニュー・編集・家族選択は下部シート。長いフォームは内部スクロールし、主要な保存／キャンセルを押せるようにする。
- 入力中のソフトキーボードで保存ボタンや入力欄が隠れないよう、可視領域に合わせる。
- 操作ターゲットは原則44×44 CSS px以上。キャンバスの拡縮後も、候補一覧とメニュー操作のタップ寸法を確保する。
- 人物カードの文字サイズはレイアウト上14px以上を基準とする。ズームによる縮小は別扱いで、読みづらい場合は詳細シート・名簿を使えるようにする。
- 縮小でカード・候補が密集した場合、透明な巨大ヒット領域を重ねず、対象選択リストまたはズームを促す。
- hoverに機能を依存させない。長押しも必須操作にしない。
- シートが開いている間はキャンバスへのタップの貫通を防ぐ。

### 8.3 パン・ズーム

- 指1本の背景移動はパン。タップとの判定閾値は画面上8pxを初期案とする。
- 2本指は中点を固定したピンチ。ピンチ後の指離しでカードタップを誤発火させない。
- PCは背景ドラッグでパン、ホイールでキャンバス内ズーム。フォーム・シート内の通常スクロールは妨げない。
- ＋／−ボタンは中心固定ズーム。初期倍率範囲案0.25〜2.5。非常に大きい家系の全体表示は0.25より小さい「俯瞰」にでき、その場合は一覧選択を主手段とする。
- 操作途中の再描画でPointer状態を引き継がず、アクティブなジェスチャーを安全に終了させる。
- ダブルタップやピンチだけに依存せず、全機能へボタンから到達可能にする。

### 8.4 [確定仕様 D13] 多言語

[確定] 固定UIを辞書化し、ja/en/viを想定。利用者の人物名等を翻訳しない。

[実装設計]

- `t(key, params)`へ統一し、HTML内の固定文字列も辞書キーで解決する。
- 言語辞書は同じキー集合を持つ。欠落時はjaへフォールバックし、開発時に検出する。
- `navigator.languages`の先頭からja/en/viを照合し、該当がなければja。
- 言語設定はメモリのみ。次回起動は再判定。JSONに言語を保存しない。
- 選択肢の標準コードのみ翻訳。自由入力のgender、marital_status、relation_typeも利用者データなのでそのまま表示。
- ID、人数、候補ラベルの埋込みはパラメーター化。文の断片の連結で語順を固定しない。
- 部分日付は不明部分を勝手に1月1日で表示せず、精度を保って言語別に整形する。
- エラー、読込失敗、削除確認、空画面、凡例、ARIAラベルも対象。

### 8.5 アクセシビリティ

人物カード・候補・家族チップをキーボードで選べる要素にする。モーダルはフォーカスを管理し、閉じたら起点へ戻す。操作状態・読込失敗を読み上げ可能な領域へ通知。関係種別・選択・無効状態を色だけで区別しない。

## 9. JSON入出力・検証

### 9.1 [実装設計 D07] 読込パイプライン

1. File選択。キャンセルなら何も変更しない。
2. バイト数を確認し、UTF-8テキストとして読み取る。先頭BOMだけは除去を許可。
3. JSON.parse。構文失敗は現在のdocument・drafts・表示を維持。
4. トップレベル、schema_version、テーブル、各フィールドの型を確認。
5. 独立した候補documentへ限定正規化を適用。
6. ID、参照、重複、日付、祖先循環、件数上限を検証。
7. データ検証成功時だけdocumentを置換し、drafts・選択・検索をクリア。
8. レイアウト計算・家系図と名簿の再描画・全体表示を行う。描画だけが失敗した場合は7.9に従い、読み込んだJSONと名簿・保存手段を保持する。
9. 補正内容は非ブロッキングの結果通知に表示する。確認待ちにはしない。

非同期処理には読込トークンを使い、ファイルAの遅い完了が、後から指定したBを上書きしないようにする。サンプルの非同期読込も同じ規則に含める。

### 9.2 許容する補正

| 内容 | 処理 |
|---|---|
| NULL許容フィールドの省略 | NULL追加 |
| 空文字列・前後空白 | 3.3の正規化 |
| 同一家族のsort_orderが飛び番・重複 | `(sort_order, id)`昇順で安定整列し、1..nへ再採番。警告 |
| auto_incrementが最大ID以下 | `max(既存値, 最大ID+1)`へ補正。警告 |
| 空テーブルでカウンターが1より大きい | 保持。過去に発行したIDを推測して巻き戻さない |

sort_orderの欠落・非数値・0以下、auto_incrementの欠落・非整数は補正対象にしない。過去に削除したIDはファイルから完全には推定できないため、正常に高いカウンターを下げない。

### 9.3 拒否するもの

- 未来／未知のschema_version。Ver.1では暗黙のマイグレーションをしない。
- 未知のトップレベルキー・レコードフィールド・auto_incrementキー。取りこぼして再保存しないため、理由を示して拒否。
- 必須のテーブル・id・外部キー・sort_order・カウンターがない。
- 重複ID、safe integerでないID、型違い、参照切れ。
- 同一家族の重複child、同じ2人の重複family、自己パートナー、自己親子、祖先循環。
- 日付エラー・生死の明確な矛盾。
- ファイルサイズ・レコード数・文字列長が上限を超える。

文字列長の初期上限案: 氏名・愛称・地名・職業は各500文字、性別・状態・関係種別は各100文字、notesは20,000文字。上限は設定で一元管理し、勝手な切捨てはしない。

未知フィールドは保存時に取りこぼさないため明示的に拒否する。未知の文字列値は許容するが、未知のフィールド名とは区別する。

### 9.4 エラー契約

```text
ValidationIssue
  severity: error | warning
  code: 安定したエラーコード
  path: 例 persons[2].birth_date
  params: field / personId / familyId等の辞書パラメーター
```

最初の50件まで表示し、総件数と省略件数を示す。エラーメッセージへレコード全体・備考・家系JSONを埋め込まない。コンソールや外部のログ収集へデータを送らない。

主なコード: `INVALID_SCHEMA_VERSION`、`INVALID_TYPE`、`UNKNOWN_FIELD`、`DUPLICATE_ID`、`REFERENCE_NOT_FOUND`、`DUPLICATE_CHILD`、`DUPLICATE_PARTNER_PAIR`、`SELF_PARTNER`、`SELF_PARENT`、`ANCESTRY_CYCLE`、`INVALID_PARTIAL_DATE`、`LIFE_STATUS_CONFLICT`、`LIMIT_EXCEEDED`。描画条件不一致はデータ検証結果とは分け、一般の描画失敗通知で扱う。

### 9.5 [確定仕様] 書出し

- documentだけを出力。仮人物・座標・世代・言語・操作状態は含めない。
- 書出し直前にも整合性を確認し、内部不整合ならファイルを作らずメッセージを表示。
- 配列はpersons.id、families.id、family_childrenの`family_id → sort_order → id`の順に並べ、UTF-8・インデント2で出力する。
- ファイル名案: `family-tree-YYYYMMDD-HHmmss.json`。名前に人物名や地名を使わない。
- Blobからローカルダウンロードし、使用後にObject URLを解放する。外部送信しない。
- 未配置人物がいる場合は「未配置N人はこのJSONに含まれません」と保存後に表示。保存の確認ダイアログや破棄確認は出さない。
- 空documentの書出しも可能。カウンターは現在値をそのまま保持。

### 9.6 初回サンプルの失敗

サンプルも通常JSONと同じ検証を通す。通信・構文・整合性エラーなら、読込失敗の表示と「再試行」「JSONを開く」「空の家系図で開始」を提供する。空documentは各テーブル空、各カウンター1。失敗を正常な空表示として隠さない。

コマンド結果は`{ok, document?, drafts?, issues, focusHint?}`等の共通形式。表示文言は返さずcodeとparamsを返す。非同期ファイル読込以外のデータ変更は順次処理する。

### 10.3 再描画手順

1. Viewportのアンカーを記録。
2. データコマンドを実行して候補検証・commit。
3. selectorsのインデックス、layoutを再計算。
4. 家系図・名簿・人物数・候補を更新。
5. 必要なら詳細シートの内容も更新し、削除対象のシートは閉じる。
6. Viewportを復元。操作状態を成功後の状態へ遷移。

全体再描画は人物関係の更新後に行う。単なるパン・ズームではDOMを全生成せず、共通transformだけ更新する。

## 11. プライバシー・安全な表示

### 11.1 [確定] データの所在

家系JSONはブラウザーのメモリと利用者がダウンロードしたファイルにだけ置く。GitHubへ実在人物を保存しない。ページを公開することと、利用者の家系JSONを公開することを混同しない。

### 11.2 [実装設計] 実装上の要件

- ライブラリ・フォント・アイコンは同梱または標準機能を使い、外部CDN・解析タグ・テレメトリー・エラー収集を入れない。
- 起動時の静的ファイル取得やGitHub Pages自身のアクセスと、利用者の家系データ送信を区別する。初回のページ取得まで「通信なし」とは表示しない。
- ユーザー入力はtextContentまたはjQueryの`.text()`で描画。名前・備考を`.html()`やSVGマークアップへ連結しない。
- notesをHTML/Markdownとして解釈しない。利用者文字列からURL、DOM属性名、CSS、イベントハンドラーを作らない。
- JSONからは許可フィールドだけ新しいオブジェクトへ取り込む。`__proto__`等の未知キーを一般的なdeep mergeへ渡さない。
- 実家系JSONをURLのquery/hash、Cookie、console、テストスナップショット、issue、コミット、スクリーンショットへ出力しない。
- サンプル・fixture・スクリーンショットは全て明確な架空情報を使う。
- 通信確認では編集・読込・保存・言語切替後に家系データを含むリクエストが発生しないことを確認する。
- Service Workerやその他のブラウザー永続化もVer.1では導入しない。アプリの設定もメモリ内にとどめる。

| L06 | 兄弟並替え後・削除後 | 左右順を更新、残った順序を保持 |
| L07 | 独立家系を接続 | 1成分に再構成、同じ人物のデータ複製なし |
| L08 | 家系分離・人物編集後の再描画 | scale保持、人物アンカーを可能な範囲で保持 |
| L09 | 多数パートナー・多数の子 | 行間レーン増加、カードを線が貫通しない |
| L10 | 対応範囲のdocument | 各person1枚で、人物集合・家族・親子関係が元データと一致 |

世代・兄弟順の特殊競合ケースは7.9に従い受入対象外。祖先循環はこれと別のデータ整合性検証として必須。通常の再婚・複数親家族・同じ世代のいとこ間の関係は、条件が両立するfixtureで確認する。

### 12.4 UI・端末

- PC: Chrome/Edge/Firefoxの実装時点の安定版で、作成→配置→接続→並替え→保存を確認。
- スマートフォン: iOS Safari実機、Android Chrome実機、縦横画面で同じ一連の操作を確認。
- 幅360px、長い氏名・ベトナム語・名無し・長い備考でフォームとシートが使用可能。
- ピンチ終了後に接続が誤発火しない。カード操作とパンを区別できる。
- ズームアウト時も候補一覧から配置できる。キャンバス上の候補の重なりで行き詰まらない。
- ja/en/viの全辞書キーが一致し、固定UIに未翻訳文字列が残らない。
- キーボードで主要操作とキャンセルが可能。削除・読込失敗時にフォーカスが消失しない。
- 家系データを含む通信、localStorage/IndexedDBへの書込がない。

### 12.5 [実装設計 D12] 性能評価

実装前に性能保証はしない。初期評価セットとして人物100・500・2,000、深い家系、横に長い家系、複数の独立家系を用意する。

- 処理時間を検証・レイアウト・DOM生成に分けて計測し、機種・ブラウザー・件数を記録する。
- 基準案: 一般的なスマートフォンで500人物の通常ケースを1秒程度以内に再描画し、パン・ズームに長い停止がないこと。未達時には上限・DOM生成・候補描画を見直す。
- 2,000人物は上限案の境界評価であり、1秒保証の対象ではない。
- 大きな入力でメインスレッドが長時間停止する場合、検証・レイアウトの分割実行やWorkerを検討する。その場合も描画結果の決定性とトークン検証を保持する。
